# core-api

Бекенд сервіс, що відповідає за основну бізнес-логіку та взаємодію з базою даних.

## Технології

- [NestJS](https://nestjs.com/)
- TypeScript
- REST API
- @nestjs/config для роботи з оточенням
- Husky + ESLint + Prettier для контролю якості коду

---

## 🚀 Запуск

1. Встановлення залежностей:

```bash
npm install
```

2. Ініціалізація husky (один раз після `npm install`, або автоматично через postinstall):

```bash
npm run prepare
```

3. Надати дозволи на всі husky-хуки (на macOS/Linux):

```bash
find .husky -type f -exec chmod +x {} \;
```

або

```
chmod +x .husky/commit-msg
chmod +x .husky/pre-commit
```

4. Запуск у dev-режимі:

```bash
npm run start:dev
```

5. За необхідності створити `.env` файл у корені проєкту:

```
PORT=8000
ENVIRONMENT=dev
```

## ✅ Git hooks (Husky)

Перед кожним комітом автоматично запускаються:

- `npm run lint:fix` — лінтер з автофіксом
- `npm run format` — Prettier форматування

> Це забезпечує єдиний стиль коду і запобігає потраплянню "сирих" змін у репозиторій.

## 📌 Правила версіонування (SemVer)

| Що зроблено у PR                                | Версія                |
|--------------------------------------------------|------------------------|
| Просто фікс, перейменування, косметика          | `0.1.0 → 0.1.1`        |
| Додано новий контролер або фічу без поломки API | `0.1.1 → 0.2.0`        |
| Зламано API або значна зміна логіки             | `0.2.0 → 0.3.0`        |
| Перехід до стабільної версії                    | `0.x.x → 1.0.0`        |

> Поки триває активна розробка, ми використовуємо `0.x.x`. Починаючи зі стабільного релізу — переходимо на `1.0.0` і далі.

## ⚙️ Автоматичне оновлення версії (CI)

Коли **PR мерджиться в `main`**, GitHub Actions автоматично:

- інкрементує patch-версію (наприклад, `0.2.0 → 0.2.1`)
- оновлює `package.json`
- створює git-тег
- пушить ці зміни в репозиторій

> Це працює лише для patch-версій.  
> Minor та major потрібно оновлювати вручну командою:

```bash
npm version minor
npm version major
```

GitHub Action лежить у `.github/workflows/release-on-merge.yml`.

## 🛠 Команди для зміни версії вручну

```bash

npm version major   # ламання API або велика зміна
```

## 📝 Коміт-повідомлення

### ⚠️ Важливо: дотримуйтеся структури повідомлень

У цьому проєкті ми використовуємо стандарт **[Conventional Commits](https://www.conventionalcommits.org/)** з обов’язковим зазначенням JIRA-ідентифікатора.

Формат повідомлення має бути таким:

```
type(WK-123): короткий опис зробленої зміни
```

### ✅ Приклади правильних комітів:

```
feat(WK-54): створити компонент списку
fix(WK-12): виправити помилку валідації
refactor(WK-90): спростити логіку форми
```

> ❗ У дужках обов’язково вказується JIRA-ключ задачі (`WK-123`, `WK-99` тощо)

---

### 📚 Типи комітів та їх призначення:

| Тип        | Призначення                                           |
|------------|--------------------------------------------------------|
| `feat`     | Додавання нової функціональності                      |
| `fix`      | Виправлення помилок                                   |
| `refactor` | Рефакторинг без зміни зовнішньої поведінки            |
| `chore`    | Технічні зміни (залежності, конфігурації тощо)        |
| `docs`     | Оновлення або додавання документації                  |
| `style`    | Зміни стилю коду (пробіли, коми, форматування)        |
| `test`     | Додавання або зміни тестів                            |
| `build`    | Зміни, що стосуються системи збірки або залежностей   |
| `ci`       | Зміни у CI-процесах (наприклад, GitHub Actions)       |

---

ℹ️ Некоректно оформлені повідомлення буде автоматично відхилено при спробі коміту.
